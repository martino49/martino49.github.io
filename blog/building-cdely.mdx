## The problem

A marketplace where several sellers share one storefront breaks the assumptions of a normal cart. When a customer buys from three vendors at once, you owe each vendor their own order, their own inventory decrement, and their own delivery tracking — and the customer expects one checkout, not three.

Cdely is that marketplace built small but honestly: four user types (customer, seller, rider, admin), a 36-table schema, real-time order tracking over Socket.io, and checkout through M-Pesa Daraja STK and Paystack. Source: [github.com/martino49/cdely](https://github.com/martino49/cdely).

## What it does

- **Multi-vendor catalog** — sellers manage their own products, inventory, and storefront presence; admins approve sellers
- **Cart splitting** — one cart becomes separate per-vendor orders at checkout, with inventory decremented per line
- **Order lifecycle** — pending → confirmed → shipped → delivered, trackable by both sides
- **Real-time tracking** — Socket.io pushes order status and rider movement, so customers watch delivery instead of refreshing
- **Notifications** — email via Nodemailer, SMS via Twilio at order transitions

## Key decisions and their tradeoffs

### One users table, four user types

The schema uses a single `users` table with a `user_type` ENUM (`customer`, `seller`, `rider`, `admin`) and role-specific tables extending it.

**The tradeoff:** every authentication path is single and every query that filters by user type is a string comparison against an ENUM — cheap, but it puts the burden of "which type is this" on application discipline rather than the schema. Separate tables per role would have enforced isolation structurally and cost four join patterns and four auth flows. For four roles with mostly shared identity data, I chose the smaller surface.

### Two schema generations of the same 36 tables, migrated by hand

The repo carries `schema.sql` and `schemav2.sql` — two generations of the same 36-table design (identical table sets, differing in later column/enum work), with `migrate.js` moving a database forward and `verify_seed.js` checking the result.

**The tradeoff:** the migration path is hand-rolled JavaScript against raw SQL files, not a versioned migration framework — so there's no down-path, no ordered history, and no test that a v1 database becomes a correct v2 database automatically. It worked; it also doesn't generalize, and having two schema files describing the same tables is debt a reviewer will notice in the first minute.

### Socket.io alongside the Express app

Real-time tracking lives on a Socket.io server colocated with the API, emitting order and rider events on state change.

**The tradeoff:** websockets make the server stateful — a single instance now carries connection state, so horizontal scaling needs a sticky or an adapter. The alternative (client polling every few seconds) would have been stateless and simpler to scale, but delivery tracking is exactly the case where a few seconds of staleness ruins the feature.

### Two payment rails, not one

Checkout integrates M-Pesa Daraja STK Push **and** Paystack.

**The tradeoff:** two integrations is double the callback, reconciliation, and failure-path work. One rail would have been half the effort — but the mobile-money-first market and the card-paying minority are both real customers, and shipping only one would have quietly excluded a payment method the platform exists to serve.

## Results

- 36-table relational schema with four user types
- 57 route handlers across marketplace, seller, rider, and admin surfaces
- Cart-splitting checkout with per-vendor orders and inventory decrement
- Real-time order/delivery tracking over Socket.io
- M-Pesa Daraja STK Push + Paystack payments
- Socket.io + Winston logging, Nodemailer/Twilio notifications, documented schema and setup (`docs/API.md`, `DB_SCHEMA.md`, `SETUP.md`)

## Known limitations and what I'd do differently

1. **No public deployment.** FinMate and EduLMS are live; Cdely is source-only — the hosting credentials for the Socket.io instance and the two payment callbacks aren't provisioned yet. It is the clearest gap in the project.
2. **No automated tests.** 57 route handlers and zero test files; the cart-splitting logic in particular deserves unit tests around the order/inventory boundaries.
3. **Hand-rolled migration instead of a framework.** Two schema generations moved forward by `migrate.js` alone — no ordered history, no down-path, no verification that a v1 database migrates to a correct v2. A versioned migration tool is the correct answer.
4. **Websocket statefulness isn't addressed.** No sticky sessions or Redis adapter is configured, so the real-time layer is currently single-instance by accident rather than by design.
5. **Last pushed February 2026.** The project has been dormant since; the honest position is that it's a strong build that hasn't been maintained — a maintenance pass with dated commits is the fix, not another feature.
