## The problem

Expense trackers fall into two camps: personal apps with no concept of a team, and enterprise finance suites that assume you have a finance department. When I needed to track my own spending while coordinating shared costs in a small team, neither fit — I needed one system where an individual user tracks personal budgets, a team leader approves their members' expenses, and an admin sees the whole picture, without five separate logins.

That requirement — one platform, two very different usage modes — drove every architectural decision in this project. FinMate is the result: live at [fin-mate-three.vercel.app](https://fin-mate-three.vercel.app), with the source at [FinMateV2](https://github.com/martino49/FinMateV2).

## What it does

Five roles — super admin, admin, team leader, team member, individual user — each with a dedicated dashboard and permission-guarded routes. Expenses with approval workflows, budgets per period, savings goals, income tracking, and Chart.js analytics.

The collaboration layer is where the roles diverge: team leaders approve their members' expenses with comments and status tracking; admins manage users, teams, and platform reports; super admins own the role and permission matrix itself, with audit logs covering every system action.

## Key decisions and their tradeoffs

### The permission matrix lives in the database, not the code

Instead of scattering `if (user.role === 'admin')` checks, FinMate stores ~20 named permissions as data and maps them to roles in a join table. Route handlers then ask "does this role hold *this permission*" instead of "is this user *this role*."

**The tradeoff:** every guarded request now hits the permission tables, so authorization is a query, not a comparison. A hardcoded role check would be cheaper and impossible to get subtly wrong — this design can misconfigure. What it buys is the ability for a super admin to change what a role can do from the UI without a deploy, which matters when the same codebase powers individual and team modes.

### JWT in HTTP-only cookies, not server sessions

Stateless auth means no session store to provision, back up, or horizontal-scale — the whole app stays deployable to a single serverless-style target with one MySQL database.

**The tradeoff:** stateless means unrevocable. A stolen token is valid until it expires, and killing a session before expiry isn't possible without extra machinery. I narrowed the exposure: 24-hour `maxAge`, `httpOnly` so JavaScript can't read it, `sameSite: 'lax'` against CSRF, and an audit log for every action so a compromised session is at least attributable.

### Auto-schema creation on boot

The app checks whether the schema exists on startup and creates the 16 tables — constraints, indexes, default roles, permissions, and role-permission mappings included — then seeds. A fresh environment needs a `.env` and a boot, nothing else.

**The tradeoff:** DDL at runtime is acknowledged-ly fragile: there's no down-migration, and schema drift between environments becomes possible. For a solo project with one database and a strict Vercel deploy target, the reliability win of "fresh clone just works" beat migration tooling. For anything with a real release pipeline, I'd use versioned migrations instead.

### Server-rendered EJS over a SPA

Every view is an EJS partial; the sidebar is a single component that adapts to role. There is no client-side router, no global state store, no API hydration layer.

**The tradeoff:** interactions that want instant feedback (chart filters, for example) cost a round trip instead of a local state update. What it bought: one deploy artifact instead of two, no duplicated validation logic between client and server, and a bundle that stays under a few tens of kilobytes.

## Results

- 5 roles and a ~20-permission matrix enforced at the route layer
- 213 route handlers across all five roles
- 16 tables with 14 foreign-key constraints
- Zero-setup deploy: schema and seed on boot
- Hardened: Helmet headers, 100 req/15 min API limiter, 10 attempts/15 min auth limiter, input sanitizing on mutation routes, parameterized SQL throughout
- Live in production, continuously available

## Known limitations and what I'd do differently

This is the part I care about, because the tradeoffs above are decisions I'd defend and the items below are debt I wouldn't.

1. **No test suite.** The repo ships with zero automated tests. Every refactor of the RBAC layer was protected only by manual clicking. A Jest + supertest suite against the permission guards would have paid for itself on the second change.
2. **JWT can't be revoked.** A 24-hour window where a compromised session stays valid is a real exposure. Refresh tokens with a jti denylist are how I'd close it properly.
3. **Runtime DDL instead of migrations.** Boot-time schema creation works until a schema change lands that an already-deployed database needs. A migrations tool removes that class of incident entirely.
4. **Secrets have a permissive fallback.** Missing configuration currently falls back to `change-me-in-production` rather than failing fast. Production should refuse to boot on a defaulted secret.
5. **No CI.** Lint, typecheck, and tests should gate every push; this repo is exactly the kind of project where a broken permission guard ships silently.

The two things this project actually proved to me: that authorization is a data problem before it's a code problem, and that "it deploys in one command" and "it can be changed safely" are different problems — the second one is what testing and migrations buy.
